# WeatherGPT

Conversational AI for weather forecasting, alerts and climate information.

Ask in five languages, by voice or by typing. Every answer is grounded in a live
tool call — the model never states a number it did not fetch. Warnings are
generated by a threshold engine, not by the model, and are rendered as
colour-coded cards inside the chat stream.

```
React + Vite + Tailwind          FastAPI + LangChain          Postgres
─────────────────────            ─────────────────           ──────────────
Web Speech API (STT/TTS)  ──►    /api/chat/stream (SSE)  ──►  PostGIS geometry
Leaflet map                      tool calling loop            TimescaleDB
severity-coloured chrome  ◄──    threshold engine        ◄──  hypertable
                          ◄──    /ws/alerts (push)
```

## 1. Run it

You need Python 3.10+ and Node 18+. Postgres and an LLM key are both optional
on the first run.

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8000
```

Open http://localhost:8000/docs for the generated API reference, and
http://localhost:8000/api/health to confirm which providers are wired in.

### Frontend

```bash
cd frontend
npm install
npm run dev            # http://localhost:5173
```

Vite proxies `/api` and `/ws` to port 8000, so both halves share one origin in
development and CORS never comes up.

That is the whole setup. The default provider is Groq running Llama 3.3 70B,
but nothing breaks if you have not added a key yet — the app detects the missing
key (or a missing provider package) and falls back to a deterministic keyword
router, logging a warning that says so. `/api/health` reports `active_agent`, so
you can always see which one is actually answering.

Weather data comes from Open-Meteo and needs no key either, so a fresh clone
works end to end with nothing configured.

## 2. Keys and environment variables

Everything lives in `backend/.env`. Nothing is required; each key upgrades one
part of the system.

| Variable | What it unlocks | Where to get it |
|---|---|---|
| `LLM_PROVIDER` | `groq` (default) \| `gemini` \| `openai` \| `ollama` \| `none` | — |
| `GROQ_API_KEY` | Llama 3.3 70B with tool calling, free tier — **the default** | https://console.groq.com/keys |
| `OLLAMA_MODEL` | Llama running fully on your own machine, no key | https://ollama.com |
| `GEMINI_API_KEY` | Gemini 2.0 Flash | https://aistudio.google.com/app/apikey |
| `OPENAI_API_KEY` | GPT-4o-mini | https://platform.openai.com/api-keys |
| `OPENWEATHER_API_KEY` | OWM as the current-conditions source | https://home.openweathermap.org/api_keys |
| `DATABASE_URL` | Observation logging, alert history, spatial queries | your Postgres instance |

Install **one** LangChain provider package only. Different providers pin
incompatible `langchain-core` versions, so having two installed at once produces
a pip dependency-resolver conflict. `requirements.txt` installs `langchain-groq`
and leaves the others commented out; if you switch providers, uninstall the old
package first.

```bash
# Default provider. Free tier, fast, native tool calling, open weights.
pip install langchain-groq
# then in .env
GROQ_API_KEY=gsk_...
```

For a fully local setup with no network egress and no account anywhere, install
Ollama from ollama.com, then:

```bash
pip install langchain-ollama
ollama pull llama3.1:8b
ollama serve
# then in .env
LLM_PROVIDER=ollama
```

An 8B model is meaningfully weaker at tool calling than Llama 3.3 70B and needs
roughly 8 GB of free RAM, so expect slower and occasionally sloppier answers.

The frontend has one optional variable in `frontend/.env`:

```
VITE_API_BASE=              # leave blank in dev; set to the API origin in prod
VITE_OWM_KEY=               # enables the precipitation radar tile overlay
```

## 3. Database

Optional. Skip it entirely by leaving `DATABASE_URL` blank — every write becomes
a no-op and the API keeps working.

```bash
createdb weathergpt
psql -d weathergpt -f db/schema.sql
```

Requires the PostGIS extension. TimescaleDB is recommended but optional — comment
out the `timescaledb` extension line, the `create_hypertable` call, the
continuous aggregate and the retention policy if you don't have it.

What the schema gives you:

- `weather_observations` — a hypertable, every served observation logged with a
  `GEOMETRY(Point, 4326)` column, chunked weekly, retained two years.
- `weather_daily` — a continuous aggregate rolling observations into daily
  min/max/mean and rainfall totals.
- `climate_normals` — seed this from IMD gridded data if you want local baselines
  instead of the reanalysis archive.
- `alert_events` — every warning the threshold engine issues, with the exact
  values that tripped it stored in a `JSONB` column.
- `alert_subscriptions` + `alert_deliveries` — who gets pushed what, within what
  radius, above what severity, with a uniqueness constraint so nobody receives
  the same warning twice.
- `subscribers_for_alert(alert_id)` — a SQL function doing the `ST_DWithin`
  radius match and the severity comparison in one query.

## 4. API

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Which providers are active |
| GET | `/api/geocode?q=` | Place name → coordinates |
| GET | `/api/weather/current` | Temperature, humidity, wind, rain rate, pressure, visibility |
| GET | `/api/weather/forecast` | Hourly + daily, 1–7 days |
| GET | `/api/alerts` | Run the threshold engine, return an `AlertBundle` |
| GET | `/api/alerts/nearby` | Recent warnings within a radius (PostGIS) |
| GET | `/api/advisory?sector=` | `agriculture` \| `urban_transport` \| `aviation` \| `marine` |
| GET | `/api/climate/compare` | This month vs an N-year baseline |
| POST | `/api/chat` | Non-streaming chat, returns reply + cards |
| POST | `/api/chat/stream` | SSE: `tool`, `card`, `token`, `done` events |
| POST | `/api/voice/transcribe` | Server-side STT fallback (needs faster-whisper) |
| WS | `/ws/alerts` | Send `{lat, lon}`, receive threshold checks on a timer |

Every location-taking endpoint accepts either `?place=Pune` or `?lat=&lon=`.

Quick check:

```bash
curl "http://localhost:8000/api/weather/current?place=Nashik"
curl "http://localhost:8000/api/alerts?place=Mumbai"
curl "http://localhost:8000/api/climate/compare?place=Pune&variable=rainfall&years=10"
curl -X POST http://localhost:8000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"Should I irrigate my field in Nashik today?","language":"en"}'
```

## 5. How the pieces work

### Tool calling

`agent.py` defines five tools: `get_current_weather`, `get_forecast`,
`check_extreme_weather`, `get_sector_advisory`, `compare_historical_climate`.
They are bound to the model with LangChain's `bind_tools`, but the execution
loop is ours — the model proposes a call, we run it, and we keep the structured
result so it can be pushed to the browser as a card at the same moment the text
is being written. Tool rounds are capped at three, then the final answer streams
back with tools unbound so it cannot loop.

The system prompt tells the model to write for the ear: no markdown, spelled-out
units, two to four sentences. That text goes straight into speech synthesis, so
asterisks and bullet characters would be read aloud.

### Warnings

`alerts.py` is deterministic. It reads current observations plus the next 24
hours of forecast and applies:

| Hazard | Warning | Watch |
|---|---|---|
| Flash flood | rain rate > 100 mm/hr | > 40 mm/hr |
| Cyclone / severe storm | 3h pressure fall > 5 hPa **and** wind > 60 km/h | wind > 40 km/h, or the pressure fall alone |
| Heatwave | daily max > 4.5 °C above the local seasonal normal | > 2.5 °C above |

The seasonal normal is computed from the reanalysis archive: the mean daily
maximum for an eleven-day window centred on today's date, across the last ten
years, at that exact coordinate. That is what makes the heatwave rule regional
rather than a fixed 40 °C cutoff.

Thresholds are settings, not constants — a state disaster authority can retune
`RAIN_FLASH_FLOOD_MM_HR` or `HEATWAVE_DEPARTURE_C` in `.env` without touching code.

Severity follows the IMD four-colour convention: green (no action), yellow (be
updated), orange (be prepared), red (take action).

### Voice and language

`useSpeech.js` wraps both halves of the Web Speech API and maps the five
languages to `en-IN`, `hi-IN`, `mr-IN`, `ta-IN`, `bn-IN`. Recognition works in
Chrome, Edge and Safari 14.1+; Firefox has none, so the mic hides itself and
`/api/voice/transcribe` is there as the server-side path
(`pip install faster-whisper`).

Synthesis voice availability varies by OS. If a language has no installed voice
the hook falls back to the browser default rather than going silent — on
Windows, install the Hindi/Tamil/Bengali language packs to get proper voices.

UI chrome is translated in `i18n.js`; the assistant's own replies are generated
in the selected language by the model.

### The map

Leaflet with a dark CARTO basemap, a severity-tinted radius circle, and
click-to-move — tapping anywhere re-anchors the conversation to that coordinate.
Set `VITE_OWM_KEY` to overlay OpenWeatherMap precipitation radar tiles.

The panel is a draggable drawer. Grab the strip on its left edge (its top edge
below 1024px, where it becomes a bottom sheet) and pull. Width is remembered for
the session. The handle is keyboard-operable: focus it and use the arrow keys,
Home and End.

Classes you can target, all defined in `src/index.css`:

| Class | What it is |
|---|---|
| `.map-drawer` | The panel element |
| `.map-drawer-handle` | The grab strip |
| `.map-drawer-grip` | The visible grip marks inside the handle |
| `.map-drawer-body` | Wrapper around the Leaflet canvas |
| `.map-drawer-canvas` | The Leaflet container itself |
| `.is-resizing` | Added to `.map-drawer` while a drag is in progress |

Sizing lives in `useDragResize` in `src/hooks/useDragResize.js` — change the
`min`, `max` and `initial` values passed from `App.jsx` to alter the limits.
`ResizeAware` inside `MapPanel` calls Leaflet's `invalidateSize` through a
`ResizeObserver`, which is what stops tiles going grey when the drawer moves.

Tested: the app boots, `/api/health` responds, and the threshold engine was fed
synthetic extreme values (118 mm/hr rain, −6.2 hPa in 3 h, 72 km/h wind, 43 °C
against a 33 °C normal) and correctly raised three simultaneous red warnings,
with all four advisory sectors producing graded output. Every frontend file

blocked by the sandbox network, not by anything in the code — they will run on
your machine.

## 7. If something breaks

**Chat returns "HTTP client not started"** — the app was constructed without its
lifespan running. Start it with `uvicorn app.main:app`, not by importing `app`
directly in a script.

**Empty reply, no cards** — check `/api/health`. If `llm_provider` is `none` the
rule-based router is answering; it handles the common intents but not open-ended
phrasing. Add a key.

**`/api/climate/compare` returns 502** — the reanalysis archive lags real time by
about five days, and the endpoint already trims the current month to account for
it. A 502 usually means the archive had no data for that coordinate; try a
nearby land point.

**Mic button missing** — Firefox. Use Chrome, or wire the UI to
`/api/voice/transcribe`.

**Frontend can't reach the API** — in dev the Vite proxy handles it. In
production set `VITE_API_BASE` and add your origin to `CORS_ORIGINS` in the
backend `.env`.

## 8. Deploying (Vercel + Render)

Frontend on Vercel, backend on Render, both fed from one GitHub repo.

### Push to GitHub

From the project root:

```bash
git init
git add .
git commit -m "WeatherGPT"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/weathergpt.git
git push -u origin main
```

Check `git status` before committing and confirm `backend/.env` is **not** listed.
It is in `.gitignore`, but a key in git history is a key you have to rotate.

### Backend on Render

1. render.com → New → Blueprint → connect the repo. It reads `render.yaml`.
2. When prompted, fill in the values marked `sync: false`:
   - `GROQ_API_KEY` — your key
   - `CORS_ORIGINS` — leave blank for now, you do not have the Vercel URL yet
   - `DATABASE_URL` — leave blank unless you added Postgres
3. Deploy. First build takes 3-5 minutes.
4. Copy the service URL, e.g. `https://weathergpt-api.onrender.com`, and confirm
   `https://weathergpt-api.onrender.com/api/health` returns
   `"active_agent":"LLMAgent"`.

Prefer the manual route? New → Web Service, set **Root Directory** `backend`,
**Build** `pip install -r requirements.txt`, **Start**
`uvicorn app.main:app --host 0.0.0.0 --port $PORT`.

### Frontend on Vercel

1. vercel.com → Add New → Project → import the repo.
2. Set **Root Directory** to `frontend`. This is the step people miss — without
   it Vercel looks for `package.json` at the repo root and the build fails.
3. Framework preset should auto-detect as Vite.
4. Add an environment variable:
   `VITE_API_BASE` = `https://weathergpt-api.onrender.com` (no trailing slash)
5. Deploy, then copy your production URL.

### Close the loop

Back in Render, set `CORS_ORIGINS` to your Vercel production URL, e.g.
`https://weathergpt.vercel.app`, and let it redeploy. Preview deployments are
already handled by `CORS_ORIGIN_REGEX`.

### What to expect

**Cold starts.** Render's free plan sleeps after 15 minutes idle and takes
30-60 seconds to wake. The first question after a quiet spell will hang, then
work. If you are demoing, load `/api/health` a minute beforehand.

**Voice needs HTTPS.** Both platforms serve HTTPS by default, so the Web Speech
API and geolocation work in production. They would silently fail over plain HTTP.

**WebSocket alerts.** `/ws/alerts` works on Render, but a sleeping service drops
the socket. The client reconnects when the location changes; conditions still
load over plain REST regardless.

**Rebuilds.** Every push to `main` redeploys both. Vercel also builds a preview
for each branch and pull request.

## 9. Rate limits

Open-Meteo's keyless tier is metered per IP. On shared hosting like Render's
free plan that IP is shared with other tenants, so you can be rate limited
without doing anything wrong. The same code runs fine on localhost because your
home IP has its own untouched quota — a difference of environment, not of code.

What the service does about it:

- **Response caching.** Geocoding and climate archives cache for 24 hours,
  current conditions for 5 minutes, forecasts for 15. The archive TTL is the
  big win: `/api/alerts` used to fire twelve requests every call, ten of them
  rebuilding a ten-year baseline that does not change.
- **Coordinate rounding.** Archive lookups snap to a ~11 km grid so nearby
  users share cache entries.
- **Retry with backoff.** 429, 502, 503 and 504 are retried three times,
  honouring `Retry-After`.
- **Stale fallback.** If retries are exhausted, the last good payload is served
  rather than failing. Slightly old weather beats no weather.
- **Slower alert polling.** `ALERT_POLL_SECONDS` defaults to 900.

If you still see 429s, set `OPENWEATHER_API_KEY`. Their quota is keyed to your
key rather than your IP, which sidesteps the shared-address problem entirely.
With a key set, both current conditions and forecasts fall back to OWM when
Open-Meteo refuses; only the historical archive still needs Open-Meteo, and
that is cached for 24 hours.

When every provider is exhausted the API returns **503** with a readable message
rather than a bare 500, so the frontend can say something useful.
